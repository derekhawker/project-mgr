# Project Principles

- For UI component boundaries, app-specific abstractions, and component styling, follow [UI component design](.agents/skills/ui-component-design/SKILL.md). When extending the presentation library in `app/packages/ui-lib/` (imported as `@ui-lib`), also follow [UI library extension](.agents/skills/ui-library-extension/SKILL.md).
- **Give coherent UI elements clear component boundaries.** Extract an element when separating its presentation or interaction makes the surrounding screen easier to understand or change. Reuse an existing component when it fits. Put product-neutral components in `app/packages/ui-lib/` and application-specific components in `app/src/components/` or beside their screen. Keep product behavior out of the UI library.
- Put application behavior, validation, state changes, persistence, and process ownership in Rust. Keep raw HTML/CSS/JavaScript as presentation and a Tauri-command adapter.
- Browser-based DOM and screenshot checks may be automated. Native Wayland layout, rendering, terminal, window, tray, and visual lifecycle acceptance remain manual; Chromium does not establish native acceptance.
- Preserve Tauri, raw HTML/CSS/JavaScript, and OpenCode-owned conversation history. Read `docs/application-workflows.md` before changing product behavior.
- Workspace/task prompts are transient inputs, never application database/file records. Log their send failures to Tauri's OS-specific `app_log_dir()/application.log` with session/error metadata only; do not write prompt contents to logs.

## Bug Discussions

- When a bug is discussed, first inspect the reported context and accessible evidence, including relevant logs and errors, without changing user data. Confirm only the material unknowns with the user before relying on assumptions or making changes: for UI bugs, the screen or interaction area, preconditions, reproduction steps, and expected versus actual behavior. Preserve safety and obtain authorization before operations that could affect user data or live services.
- For native initial-prompt failures, inspect Tauri's `app_log_dir()/application.log`: on Linux, `${XDG_DATA_HOME:-$HOME/.local/share}/dev.opencode.projectmgr/logs/application.log`; on macOS, `~/Library/Logs/dev.opencode.projectmgr/application.log`; on Windows, `%LOCALAPPDATA%\dev.opencode.projectmgr\logs\application.log`. An application directory override changes the location to `<override>/logs/application.log`. The file may not exist until a failure is logged; inspect terminal stderr and the UI error too. Never copy prompts, credentials, or other secrets into reports or logs.
- For frontend command failures, inspect `window.appDiagnostics()` in the browser/WebView developer console, or `agent-browser console` in the mock browser. These bounded, in-memory records contain command names and categories only and reset on reload; they do not cover failures before frontend startup. UI and other console/stderr messages may contain sensitive details, so review before sharing.

## UX Terms

- For UI names and locations, consult `docs/ux/glossary.md` and the screen map in `docs/ux/index.md` before asking the user to identify an area.
- **Workspace:** A project grouping that knows about zero or more repositories and may contain zero or more tasks. Its repository associations are working context; existing repositories stay where they are unless the user explicitly chooses otherwise.
- **Task:** An optional, independently progressing unit of work nested under one workspace. It may use one or more repositories associated with that workspace; managed worktrees go under `<task-home>/worktrees/`.
- **Quick Request:** A named one-off tracked item under the special Quick Requests workspace. It is important work with its own status and lifecycle, not a generic label for a user's text or an OpenCode interaction.
- **Prompt:** Text supplied to OpenCode. The initial user text is the **original prompt**; text prepared for a new session is the **starting prompt**. A prompt is not a product record.
- **Interactive terminal:** The user's live interface to an OpenCode session or interactive tool process. Users watch progress and handle follow-ups, approvals, input, and changes there. The terminal is not an app-rendered transcript or a background-only process.

## Implementation

- Default user-facing Tauri backend commands to async orchestration. Put blocking Rust work on a bounded blocking executor. Make explicit exceptions for UI-thread operations and measured, high-frequency lightweight commands.
- Treat `npm run live --prefix app` as a persistent, user-owned development runtime: reuse it and let frontend changes hot-reload. Preserve its launch script and running process; restart or change either only when the work requires it, and explain why first.
- When adding or moving frontend files, follow [frontend organization and naming](app/README.md#frontend-organization): colocate screen code in `app/src/views/<area>/`, use exact-name PascalCase component files, and keep plain JavaScript modules camelCase.
- Before implementation, understand how the intended behavior could work end to end within the current architecture. Identify whether the feature extends an existing feature or calls for a different organization of code. Refine this understanding as implementation reveals more.

## Code Indexing

- When using Codesitter in this repository, keep the frontend and Rust indexes separate: index `app/` with `--lang js,ts,tsx`, and `app/src-tauri/` with `--lang rust`. These are distinct project roots, each with its own `.codesitter` index; run queries against the matching root and use file paths relative to that root. `app/` is the frontend root because it includes its source, tests, and HTML entry point; `app/src-tauri/` is the Rust root. Codesitter skips generated `target/` directories.

## Testing

- For behavioral fixes, run a regression test that reproduces the reported behavior before changing production code; confirm it fails for that behavior, then apply the fix and confirm it passes. Add a test if an existing one cannot reproduce it. Prefer testing real behavior over checking source text. For visual-only changes, follow the appearance rule below.
- **Cover risks, not functions.** Before adding tests, identify the changed rule and the regression an existing test would miss. Extend an existing scenario when it can prove the rule clearly. Add another layer only for a distinct risk; neither test counts nor coverage percentages justify duplicate assertions.
- **Use the simplest test that covers the risk.** Use input/output tables for pure Rust rules, the production store with isolated SQLite for persistence, and temporary real Git/filesystem fixtures for Git/path safety. Use file-backed SQLite for reopen and migration tests. A selection-persistence test should not provision a clone or start a process.
- **Cover both sides of changed Tauri commands.** Rust tests cover behavior and serialized results; frontend tests cover command names, payloads, and result/error handling. Reuse shared contract checks and, where practical, Rust-produced values in frontend validation. Add command-specific cases for distinct contract risks, not another backend scenario matrix.
- **Keep test fixtures small and reusable.** Reuse small record constructors and fixture helpers; show only scenario-specific differences in each test. Let tests set up only the database, repository, worktree, or session they need rather than building the whole application by default. Each test owns its mutable state and temporary-resource cleanup. Share setup, never the production calculation of an expected answer.
- **Test the real workflow.** When Tauri setup prevents a workflow from being tested directly, extract the necessary Rust service and keep the command handler thin. Replace only external operations needed to control failures; keep real store and Git integration coverage. Do not rebuild the workflow in the test or add a trait or mock for every internal call. Scope testability changes to the feature.
- **Spend extra cases on side effects.** Cover relevant success, rejection before mutation, partial failure, and retry/reopen recovery paths. Check persisted ownership, retained user files, atomicity, and absence of duplicate work. Inject failure where the side effect can fail, then assert recovery through the production entry point. Keep independent failure scenarios independently runnable.
- **Test usability, not visual preferences.** Do not write tests merely to lock down CSS, theme values, classes, computed styles, exact positions, or visual preferences. Test meaningful behavior, such as whether a control remains reachable, when there is a distinct risk. Inspect layout in a browser and check native Wayland appearance manually; a visual-only change does not need a regression test.
- **Assert behavior, not source spelling.** Use production functions or DOM events for frontend behavior; reserve source-text checks for command inventories and architecture rules. Assert ordering only when correctness requires it.
- **Keep external-service tests manageable.** Reuse a scripted local HTTP server with the real client instead of writing socket parsing per test. Give waits deadlines and clean up fixture processes on failure. Keep tests against the installed OpenCode CLI and server explicit and separate from fast deterministic tests; mocks do not replace them. Check provider-dependent behavior manually when automation cannot validate it.
- **Keep migration tests historical.** Build the database using schema/migrations through version N, seed representative data, then run the production upgrade. Do not manufacture an old database by dismantling the latest schema: a new migration should not force repairs to old test setup.

## Post-Implementation

- Validate the intended end-to-end behavior, not just the edited functions. Run focused tests while iterating, then applicable broader and integration suites before completion. Report what actually ran and any manual or unvalidated paths; database and data-format tests do not prove that native commands or the GUI work. For workflow coverage changes, update affected rows and gaps in `docs/integration-test-matrix.md`.
- Review relevant documentation against the implemented feature. For UX changes, consult `docs/ux/index.md` and the specification for the affected screen or interaction area; update the area-specific document and keep the index in sync when the UX structure or listed areas change. Update other relevant documentation where behavior, workflows, or terminology have changed. If no documentation change is needed, record why. Do not consider the feature complete until this review is done.
- Consider the feature complete only after the end-to-end validation and documentation review are done.
