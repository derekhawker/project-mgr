# Handoff

## Context

The conversation established requirements for a visual GUI that manages work performed through OpenCode sessions. No application code has been written in this session. The current working directory was empty before this handoff document was created.

The agreed vocabulary is:

- **Workspace**: a persistent top-level area for a kind of work, such as a Todo app or movie tracker.
- **Task**: a unit of work belonging to exactly one workspace.
- **Quick Requests**: a special workspace containing short-lived one-off tasks.
- **Session**: an OpenCode conversation attached to a workspace or task.
- **Home folder**: the filesystem location for a regular workspace or task's notes, resources, and working environment.
- **Repository catalog**: the global catalog of known repositories, their paths, and concise purposes.

## Agreed Product Model

The GUI is the primary way to create work. A user enters a prompt, while controls outside the prompt choose regular tracked work versus a quick request and supply preferences.

The hierarchy is fixed at one level:

```text
Workspace
└── Task
```

- Workspaces may have their own OpenCode sessions for planning, coordination, and inspection.
- Tasks may have multiple sessions. Starting a new session means starting a fresh conversation in the same task workspace while retaining existing file changes.
- Tasks cannot contain child tasks.
- A workspace cannot be completed while it has active tasks.
- Completing the last task does not complete the workspace automatically. More tasks may be added later.
- Finite projects and ongoing activities use the same model.

## Sessions and GUI Behavior

- Embed a fully interactive OpenCode terminal in the GUI.
- Let the user choose an available model for each new request. An app-owned setting preselects `openai/gpt-6-luna` by default; Rust must bind the chosen model explicitly and never fall back to OpenCode's configured default.
- Creating a quick request automatically opens its terminal and streams the response in real time.
- Keep workspaces prominent in persistent left navigation, with each workspace's tasks nested directly beneath it. Include idle workspaces; do not require a separate all-workspaces summary screen.
- Show Quick Requests from the last 24 hours in a separate, lower-priority section of the left navigation. Quick Requests must not dominate the main content area.
- In the selected workspace view, give the active OpenCode terminal almost all of the main/right pane; keep workspace and task controls compact.
- Closing a terminal tab hides only the view; OpenCode continues running.
- Closing the GUI does not stop OpenCode. Reopening reconnects to running sessions and reports their state.
- Show status indicators for running sessions, sessions waiting for user input, and results ready for review.

## Quick Requests

Quick Requests is a special workspace. Its recent requests appear in the
secondary left-navigation section, separate from the primary workspace/task
tree. The selected workspace, not Quick Requests or a workspace summary, is the
main application view.

- Each quick request is a task under Quick Requests.
- All quick-request sessions use one shared directory.
- Quick requests do not receive individual home folders.
- A completed answer does not immediately hide a request; the user can dismiss it.
- The request expires 24 hours after creation. Follow-ups do not reset this clock.
- Running requests and requests waiting for input remain visible.
- Hidden requests remain available in history.
- A quick request can be promoted to regular tracked work. Promotion preserves its sessions and history, removes quick-request expiry, and creates a dedicated home folder for future sessions. Earlier sessions keep their original working directory.

## Regular Workspaces and Tasks

Every regular workspace and task gets a dedicated home folder by default. The folder provides a stable OpenCode starting directory and holds notes and supporting resources.

For a multi-repository software workspace, the intended shape is conceptually:

```text
todo-app/
├── notes/
├── repos/
│   ├── frontend/          main-branch checkout
│   └── backend/           main-branch checkout
└── tasks/
    └── account-sync/
        ├── notes/
        └── worktrees/
            ├── frontend/  task branch
            └── backend/   task branch
```

- Workspace-level sessions inspect main-branch checkouts and handle planning/coordination. They may edit workspace notes and requirements.
- Task-level sessions implement code in task-specific branches and worktrees.
- All sessions for one task share that task's workspace and worktrees.
- Existing repositories may remain at their current locations; the organizational hierarchy does not require moving them.
- A task may span multiple repositories.

## Repository Catalog and Setup

Maintain a global repository catalog with repository identity, local location, and concise purpose.

- The user can choose folders to scan for repositories.
- OpenCode generates concise purpose descriptions during discovery.
- Repositories attached or created later are added to the catalog.
- Workspaces reference catalog entries; tasks record their concrete branches and worktree paths.
- Prompt-based inference is the normal repository-selection path.
- Explicit repository attachment is also supported.
- Right-clicking a workspace offers **Create new task**, with the workspace context already selected.

For regular software task creation:

1. The GUI creates the task home folder and starts an OpenCode session there.
2. The GUI supplies the prompt, available repository context, setup instructions, and preferences.
3. OpenCode determines the relevant repositories.
4. OpenCode creates required branches and worktrees.
5. The GUI records the resulting repositories, branches, and paths.

Git's restriction against checking out the same branch in multiple worktrees must be respected. A workspace's repository checkout is intended for main-branch inspection; task worktrees isolate concurrent implementation work.

## Completion and Cleanup

- Completion mainly hides work from the active GUI; history remains accessible.
- A task may be completed before its code is committed or merged.
- Completion does not commit or merge code.
- Completed tasks cannot be reopened. Further work starts as a new task.
- Completing a task queues automatic background cleanup.
- Cleanup removes a worktree only when it is clean and no session is using it.
- Branches are retained after worktree removal.
- Worktrees with uncommitted changes or new files remain in place and stay associated with the completed task.
- No automatic backup/restore or worktree recreation feature is required initially.

## Persistence

Management changes save automatically. Persist workspaces, tasks, relationships, completion/visibility state, session associations, home folders, repository bindings, branch/worktree paths, and preferences in local application state.

Do not use a shared Git repository for project management. Notes and resources are ordinary files. Non-code resources do not receive Git history by default. Software repositories continue using Git, and OpenCode conversation history is independent of Git.

## Implementation Status and Remaining Work

The product model and main technical direction are settled. Use
[`docs/implementation-handoff.md`](docs/implementation-handoff.md) for the
ordered production tasks, dependencies, and implementation/validation protocol;
use [`docs/application-workflows.md`](docs/application-workflows.md) for the
normative behavior. Do not reopen these decisions as unresolved design questions:

- Use Tauri with Rust-owned application behavior and raw HTML/CSS/JavaScript
  presentation.
- Use SQLite for management state; OpenCode remains the owner of conversation
  history.
- Use an app-owned OpenCode server/API runtime and interactive TUI terminal, with
  the Tauri application owning child-process lifecycle.
- Use structured OpenCode setup reports, validated by Rust, for repository,
  branch, and worktree associations.

These choices still require implementation and acceptance evidence. In
particular, the current P-00 integration/registration criteria and the ordered
I-00 through I-12 production tasks remain governed by the implementation
handoff. Keep GUI, terminal, window, tray, and lifecycle acceptance manual on
Wayland unless the user explicitly reopens that decision.

Do not add more hierarchy levels or reopen behavior unless the user explicitly changes the requirements.
