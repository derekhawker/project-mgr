# UI component interaction research

Scope: `app/packages/ui-lib/` interaction semantics and defaults, checked against W3C APG patterns and MDN's native-element references. This is a findings note, not a claim of full conformance; user-agent behavior and actual labels/content supplied by callers matter.

## Findings

### Modal and drawer

- `Modal` and `Drawer` call `showModal()`, so the browser provides modal top-layer behavior, makes the rest of the document inert, supports Escape through the `cancel` event, and manages the dialog focus sequence/restoration. The handlers prevent the browser's default close and ask the controlled owner to close; this is consistent with that ownership model. [MDN: `<dialog>`](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/dialog); [W3C APG: modal dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)
- Both components treat a click on the dialog element itself (backdrop hit) as a close request. This is a deliberate *light-dismiss* policy, not a modal-dialog requirement: APG specifies Escape and containment, while native `showModal()` defaults to close-request dismissal and MDN distinguishes outside-click dismissal as a separate policy (`closedby="any"`). Current manual backdrop handling adds that policy explicitly. Decide whether backdrop clicks should dismiss; preserve Escape and a visible close mechanism regardless. [MDN: `<dialog>`](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/dialog)
- APG recommends a visible button that closes each dialog and requires an accessible name (`aria-labelledby` to a visible title or `aria-label`). The `Drawer` supplies a close button, but its fixed English name may be inappropriate for localization. `Modal` supplies no close button itself and relies on children. Both allow no accessible name when neither `title` nor `aria-label` is given. Treat named-dialog input as a caller/component contract; decide whether `Modal` should provide a close control or continue requiring one in its content. [W3C APG: modal dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/); [MDN: `<dialog>` accessibility](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/dialog#accessibility)
- `Modal`/`Drawer` animate neither overlay nor backdrop. `Drawer` has a 180ms transform transition plus `prefers-reduced-motion: reduce { transition: none; }`; this honors the reduced-motion preference for its current motion. No standard requires an entrance/exit animation. Adding dialog exit animation is not a simple CSS transition because closing removes the dialog from the top layer; MDN documents discrete `display`/`overlay` transitions and `@starting-style` for supported browsers. [MDN: `<dialog>` animations](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/dialog#animating_dialogs); [MDN: `prefers-reduced-motion`](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion)

### Action menu / disclosure

- `ActionMenu` is implemented as native `<details>/<summary>` and accurately describes itself as a disclosure. Native disclosure provides keyboard toggling and exposed open state; APG's disclosure pattern requires a button-like control and expanded state, which the native element supplies. It does not need custom menu roles or arrow-key management when it is simply a disclosure group. [MDN: `<details>`](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/details); [W3C APG: disclosure](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/)
- Despite the name, it is not an APG menu button/menu: it does not expose `aria-haspopup="menu"`, a `menu` role, or menu-style keyboard focus/navigation. This is not a defect if the actions are ordinary grouped links/buttons inside a disclosure; changing to menu semantics would require implementing the full menu pattern. [W3C APG: menu button](https://www.w3.org/WAI/ARIA/apg/patterns/menu-button/)
- No outside-click dismissal is implemented. `<details>` has no standard requirement to close on outside click; this is a product choice. The current action handler closes only after enabled buttons, not links. Decide whether links and/or outside clicks should also dismiss. The summary's `aria-label` is provided from `props.label`; callers should supply a useful label (the visible summary text already names it if no override is set).
- No animation is present. Animation is optional. If added, honor `prefers-reduced-motion`; details content animation support is evolving, so retain a usable immediate state change. [MDN: `<details>`](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/details); [MDN: `prefers-reduced-motion`](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion)

### Tabs

- `Tabs` follows the APG automatic-activation model: selection updates on arrow-key focus and click, wraps arrows, supports Home/End, gives only selected tab `tabindex=0`, links tabs/panels, and makes panel focusable. Automatic activation is recommended when panels appear without noticeable latency; confirm this remains true for caller panels. [W3C APG: tabs](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/)
- The component supports vertical orientation with Up/Down; horizontal lists correctly leave Up/Down alone. It sets `aria-orientation`, selected state, and tab/panel relationships. A tablist name is supplied using either `label` (`aria-label`) or `labelledBy` (`aria-labelledby`); callers must provide one because APG requires a name. If the controlled selection is absent or disabled, the first enabled tab remains the roving keyboard entry point; the caller still owns establishing a valid selection. With an empty tabs list there is no selected tab; callers should avoid that state.
- No animations exist or are required by APG. If panel transitions are introduced, honor reduced motion and do not delay activation/focus. [W3C APG: tabs](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/); [MDN: `prefers-reduced-motion`](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion)

## Recommended defaults and open choices

1. Keep native `dialog` and `details` primitives; make accessible-name requirements explicit in component contracts and ensure every rendered dialog has a visible close path.
2. Keep backdrop dismissal only if it matches product expectations. It is optional, and unlike Escape/keyboard access it is not an APG requirement. Make tests and docs reflect the chosen policy.
3. Keep `ActionMenu` a disclosure unless product requirements truly call for application-menu semantics; decide whether outside clicks and link activation close it.
4. Require accessible tablist labels and keep automatic activation only for prompt panel switching.
5. No animation is the simplest baseline. For any motion retained or added, honor `prefers-reduced-motion`; test the preference and visual/native overlay behavior manually on Wayland as project policy requires. No automated visual acceptance is implied here.
