# Compile-time CSS for SolidJS and Vite

Research date: 26 October 2026. This compares authoring and runtime tradeoffs, not measured performance. The app's documented Solid migration uses Vite 6; check package compatibility against the actual lockfile before adopting any option.

## Recommendation

Use **CSS Modules and CSS custom properties as the baseline**, especially when preserving existing CSS is important. If typed theme contracts and TypeScript-authored component styles justify a new dependency, trial **vanilla-extract** first. It offers framework-independent static CSS, scoped variables and an explicit runtime-variable API without requiring an atomic styling system. Choose **Panda CSS** instead when a token-driven utility/recipe system is a deliberate design-system goal and its extraction constraints and generated tooling are acceptable. Neither choice automatically makes rendering faster; measure the app.

## Comparison

| Option | Build and Solid/Vite fit | Runtime values and costs | Tradeoff |
| --- | --- | --- | --- |
| **CSS Modules** | Vite directly supports `.module.css` imports, which return scoped class mappings; Solid documents the approach. [Vite](https://vite.dev/guide/features.html#css-modules), [Solid](https://docs.solidjs.com/guides/styling-components/css-modules) | Ordinary CSS custom properties can be set reactively with Solid's `style` object; no CSS-in-JS generator is required. [Solid style](https://docs.solidjs.com/reference/jsx-attributes/style) | Minimal migration and tooling; no built-in typed token contract or variant API. |
| **vanilla-extract** | Framework-independent `.css.ts` styles generate CSS at build time; the official Vite plugin targets applications. [Project](https://github.com/vanilla-extract-css/vanilla-extract), [Vite integration](https://vanilla-extract.style/documentation/integrations/vite/) | `createVar`/theme contracts supply scoped CSS variables; optional `assignInlineVars` or `setElementVars` assigns runtime values. The dynamic helper is a runtime dependency; recipes and other optional helpers can also add runtime work. [Dynamic API](https://vanilla-extract.style/documentation/packages/dynamic/), [recipes](https://vanilla-extract.style/documentation/packages/recipes/) | Typed CSS and contracts, but styles live in separate TypeScript files and require a plugin. The Vite plugin explicitly does **not** support building libraries; use its documented Rollup integration for a separately distributed library. |
| **Panda CSS** | Official Solid/Vite setup uses PostCSS and generated `styled-system` code. CSS is statically extracted. [Solid setup](https://panda-css.com/docs/installation/solidjs), [styled system](https://panda-css.com/docs/concepts/styled-system) | Default `css()` calls resolve class strings at runtime. Panda v2 offers opt-in `@pandacss/vite` source transforms for statically resolvable calls; unresolved calls remain runtime calls. An unknown runtime value does not magically generate CSS: use variables or pre-generate finite variants with `staticCss`. [Transforms](https://panda-css.com/docs/styling/source-transforms), [dynamic styling](https://panda-css.com/docs/styling/dynamic-styling) | Rich tokens, recipes and utilities, with codegen and extraction rules to learn. The Solid setup documents PostCSS; verify the optional v2 Vite transform and plugin ordering with this app's Solid/Vite versions before relying on it. |
| **UnoCSS** | On-demand utility CSS, with an official Solid guide and Vite plugin; the guide says to put Uno before the Solid plugin. [Solid guide](https://docs.solidjs.com/guides/styling-components/uno), [Vite integration](https://unocss.dev/integrations/vite) | Static utilities generate CSS; dynamically constructed utility names may not be detected. Use complete literal alternatives or a safelist for finite choices, and CSS variables for open-ended values. Uno also offers a separate runtime generator, which changes the runtime cost. [Extraction](https://unocss.dev/guide/extracting) | Good for utility-first authoring; less suited if the goal is retaining existing semantic component CSS. By default `.js` and `.ts` files are not pipeline extraction targets, so configure them if class definitions live there. |

## Override pattern

Keep selectors, states and defaults in static CSS; expose only intended customization points as custom properties. Solid supports reactive `style` objects with dash-separated keys and custom properties. For example, a module rule can use `background: var(--surface, #222)`, while a component supplies `style={{ '--surface': props.surface }}`. A nullish value removes the inline property, allowing the CSS fallback or inherited value to apply. [Solid style](https://docs.solidjs.com/reference/jsx-attributes/style)

With vanilla-extract's scoped `createVar`, use `assignInlineVars` rather than treating its `var(...)` reference as a raw property name; its contract overload requires all contract values. Check Solid's `style` typing and reactive updates in a small integration spike, since the upstream JSX examples use React. [Dynamic API](https://vanilla-extract.style/documentation/packages/dynamic/)

For finite states, switch among statically defined classes or attributes; for arbitrary user/runtime values, update a variable. Inline overrides participate in the normal cascade and can mask stylesheet declarations on the same element, so define the intended override scope and fallback. Variable updates still cause browser style recalculation and possibly layout/paint; compile-time extraction does not eliminate those costs.

## Validation before adoption

Build one representative existing component and a theme override using the actual app versions. Verify Vite dev/HMR and production output, reactive changes and removal/fallback, variant coverage, CSS ordering and dark/theme scope. Compare production CSS and JavaScript bytes, cold builds and HMR, and representative interaction performance against the existing baseline; inspect emitted code instead of assuming optional helpers are tree-shaken. Validate visual and native behavior manually on Wayland. No package was installed, benchmark run, or integration tested for this research.
