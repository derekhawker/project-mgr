## Approved Technical Direction

- **Desktop framework:** Tauri.
- **Frontend:** raw HTML, CSS, and JavaScript. Do not introduce Electron, React, Svelte, or another frontend framework unless the user explicitly reopens this decision.
- **Application logic:** Rust in the Tauri core.
- **Management persistence:** SQLite for workspaces, tasks, repository catalog entries, session associations, settings, and cleanup state. Notes and resources remain ordinary files.
- **OpenCode integration:** use the OpenCode server API for session creation, prompts, history, status, and events, while providing the interactive OpenCode terminal experience inside the GUI.
- **Workspace setup reporting:** use a dedicated structured registration tool. OpenCode should call it to report repositories, branches, and worktree paths; Rust validates the calls and writes authoritative associations to SQLite.
- **Execution lifecycle:** keep the Tauri application process running when its window closes, optionally using a tray presence. A full application quit stops background execution. Do not add a separate background service for the initial design.
- **OpenCode installation:** use the user's existing OpenCode installation, with a startup compatibility check. Do not bundle OpenCode initially.
- **Conversation history:** OpenCode owns conversation history. SQLite stores associations to OpenCode session IDs; the GUI retrieves history through the API rather than maintaining duplicate transcripts.
- **Current interface direction:** use persistent workspace/task navigation and a selected-workspace main pane, not a dashboard; recent Quick Requests are secondary navigation. See [`docs/mockups/project-manager-low-fi.svg`](docs/mockups/project-manager-low-fi.svg) for an exploratory reference, not a final visual specification.
- **Initial platform:** Linux. macOS compatibility must remain a design constraint: raise any proposed choice that would be incompatible with or materially complicate macOS immediately. macOS does not need first-release support, but avoid silently taking Linux-only decisions.

## Important Constraints

- Keep the hierarchy at exactly `Workspace -> Task`; tasks cannot contain tasks.
- Completed tasks cannot be reopened. Further work starts as a new task.
- Quick Requests are a special workspace, use one shared directory, and expire 24 hours after creation.
- A task may span multiple repositories and its sessions share its task workspace/worktrees.
- Workspace sessions inspect main-branch checkouts and plan; task sessions implement changes in task worktrees.
- The GUI must not require a shared Git repository for management state.
