# UX Redesign Handoff

## Purpose

Redesign the application as one end-to-end product effort. The work includes
interaction, application behavior, and validation; it is not a frontend-only
pass. The concise UX requirements are in [`docs/ux/index.md`](docs/ux/index.md)
and its linked screen specifications.

The parent `implementation-handoff.md` records the completed original build and
is historical context, not the plan for this redesign.

## Product direction

- A workspace is a project grouping. It is useful with or without repositories
  or tasks.
- Tasks are optional, belong directly to a workspace, and support independent
  parallel work, including work across multiple repositories.
- **New work** is a navigation dropdown with explicit workspace, contextual task,
  and Quick Request choices. The chosen flow opens a modal, captures a prompt,
  and reviews an OpenCode proposal where applicable.
- Workspaces and tasks provide full-size interactive OpenCode terminals.
  Terminal tabs belong to their owner, remain available while the app is open,
  and are not required to restore after shutdown. The terminal owns interaction
  and process lifecycle.
- Quick Requests stay prominent at the top of navigation and have a separate
  full-list view. Change review is a conventional two-way diff against current
  `origin/main`; README files are shown by full path; repo scripts run in
  interactive terminals.

## UX deliverables

This is the scope of the redesign. The existing production UI is implementation
baseline only; its current screens and interaction flow are not acceptance
criteria. Do not spend this effort polishing the old direction or adding
unrelated reliability features. Change Rust behavior only where the agreed UX
requires it, with command-boundary tests for that behavior.

Deliver one user-visible end-to-end slice at a time. Each slice includes
necessary Rust behavior, Tauri boundary, frontend experience, and automated
tests; do not split those into separate frontend/backend/testing projects.
Deliverable 2 follows Deliverable 1. The user identifies Deliverables 3
(Workspace tasks) and 4 (Multiple-repository workspaces) as the highest
priority, and wants to work on Deliverable 4 first, followed by Deliverable 3.
Deliverables 5 (Change Review) and 6 (Repository tools) follow those. Deliverables
7–9 (Quick Request search, README reader, and OS handoff) may be done in any
order, subject to dependencies and completing their UX specifications where
needed. Confirm the scope of Deliverables 3 and 4 with the user at preflight to
separate unfinished requirements from the already-completed baseline. Complete
each deliverable's own acceptance gate before calling it done.

### Deliverable 1 status

Deliverable 1 implementation is complete against [New Work](docs/ux/screen-new-work.md),
[Workspace/task workbench](docs/ux/screen-workbench.md), and
[No selection](docs/ux/screen-no-selection.md). The gap review found these
issues, now addressed in the production path:

- New replaced the current destination instead of opening over it; New and its
  proposal review now live in one modal.
- First-run and navigation exposed a separate name-first workspace form; that
  path is removed, leaving the specified simple no-selection message and New.
- Confirmation stopped at a separate “starting prompt · not sent” action; the
  app now opens the tracked terminal and sends the reviewed prompt automatically,
  reporting failures without claiming the prompt was sent.
- Workspace/task selection did not restore an owner-tracked session; navigation
  now returns sessions grouped by their exact owner and the UI restores only an
  associated session, preserving an open tab choice.
- Task creation trimmed the original prompt before storing it; the original
  text is now passed transiently without trimming while whitespace-only prompts
  remain invalid.
- Workspace/task starting prompts are transient inputs, not SQLite records. A
  forward migration removes legacy prompt columns/table, and send failures are
  logged to the OS app log with session/error metadata and prompt redaction.
- The workbench now has a terminal-only, unpadded, full-height terminal area;
  xterm's required stylesheet is loaded, tracked session tabs are named
  **OpenCode**, and the New-work dialog has padded, independently scrolling
  content with a stable action footer.

Automated validation passed: Rust unit/integration tests, frontend tests, the
production build, formatting, and `git diff --check`. Documentation has been
reviewed and updated. Before any Deliverable 2 implementation, first review the
relevant UX specs—[Quick Requests](docs/ux/screen-quick-requests.md) and [New
Work](docs/ux/screen-new-work.md)—against that deliverable's scope and record
any clarifications. The user has confirmed Deliverable 1 is finished.

### Deliverable 2 preflight review

The Deliverable 1 manual gate is user-confirmed complete. The user clarified
Deliverable 2's Quick Request behavior:

- The persistent navigation's **New work** control is a dropdown offering
  workspace, contextual task, and Quick Request choices. The prompt form itself
  does not contain a work-type selector.
- Quick Request setup is a two-step flow: the first step resolves only a working
  directory from the registered repository catalog (falling back to the shared
  default Quick Request directory); the user confirms it, then the original
  prompt starts unchanged.
- The Quick Request destination keeps the app shell/navigation visible and uses
  the terminal's available-height layout, with no owner/task toolbar or tabs.
  **Back to Quick Requests** returns to the list without closing the terminal.
- When no registered repository is selected, use the special
  `<configured OpenCode Projects root>/Quick Requests/` folder, not a temporary
  directory. Existing session directories remain exact and restorable.
- New-work capture modals are compact and identify **Workspace**, **Task**, or
  **Quick Request** in the heading and prompt instruction. The proposal/review
  modal expands and names the selected work type before confirmation.
- Recent navigation shows items created within 24 hours, uses workspace-link
  styling, and has no delete action. The full Quick Requests list shows all
  retained items and offers one confirmed **Delete** action per row. Deletion
  removes local app records but preserves OpenCode conversation data.
- The compact **All** icon button sits beside the Quick Requests heading. The
  full-list destination has no Back button; the persistent navigation remains
  available. Pin **New work** to the bottom of that navigation and open its menu
  upward as an overlay.
- Persist each Quick Request's original prompt in a dedicated SQLite table linked
  to its task; keep workspace/task prompts transient. Use the stored Quick
  Request prompt in its list and initial-send/retry flows.

Updated the Quick Request/New Work UX specs, UX index, application workflows,
and terminal integration notes to match. Quick Request list search is deferred
to Deliverable 3. The consolidated Wayland acceptance is recorded below.

For every deliverable, implement its documented behavior end to end through the

## Manual validation gates — nine total

Perform one consolidated manual Wayland validation for each deliverable:

1. **Workspace/task workbench:** after item 1 is complete, validate workspace
   and task creation, selection, and interactive OpenCode work.
2. **Quick Requests — complete:** user-confirmed on Wayland. Acceptance covers
   recent navigation, persistent navigation from the full-list destination,
   interactive request work and terminal sizing, modal and directory flows, and
   confirmed deletion. Full-list rows show a separate Open button, plain
   ellipsized prompt text, and Delete.
3. **Workspace tasks:** validate the user-confirmed task workflows and
   independent task/session lifecycle.
4. **Multiple-repository workspaces:** validate association with multiple
   repositories and correct repository context throughout the agreed workflows.
5. **Change Review:** validate repository/file discovery, diff presentation, and
   the agreed failure cases.
6. **Repository tools:** validate tool grouping, launch in the correct repo
   context, and interactive terminal behavior.
7. **Quick Request full-list search:** validate matching, empty results, and
   clearing behavior once those details are specified.
8. **README reader:** validate full-path discovery, file selection, contents,
   and return to the still-open terminal.
9. **OS handoff:** validate the specific operating-system interaction after its
   behavior and acceptance criteria are documented.

These are the nine planned manual validations. Run automated tests for each
end-to-end slice as it is completed. If a manual gate finds a defect, fix it
before proceeding; retest that gate rather than starting the next delivery item.
