# UX Redesign Handoff

## Purpose

Redesign the application as one end-to-end product effort. The work includes
interaction, application behavior, and validation; it is not a frontend-only
pass. The concise UX requirements are in [`docs/ux/index.md`](docs/ux/index.md)
and its linked screen specifications.

The parent `implementation-handoff.md` records the completed original build and
is historical context, not the plan for this redesign.

## Product direction

- A workspace is a project grouping. It is useful with or without repositories
  or tasks.
- Tasks are optional, belong directly to a workspace, and support independent
  parallel work, including work across multiple repositories.
- One **New** action captures intent. A structured LLM proposal is reviewed
  before a workspace, task, or Quick Request is created. Preserve the original
  request and show proposed context and effects. The starting OpenCode prompt is
  editable and remains unsent until the user submits it.
- Workspaces and tasks provide full-size interactive OpenCode terminals.
  Terminal tabs belong to their owner, remain available while the app is open,
  and are not required to restore after shutdown. The terminal owns interaction
  and process lifecycle.
- Quick Requests stay prominent at the top of navigation and have a separate
  full-list view. Change review is a conventional two-way diff against current
  `origin/main`; README files are shown by full path; repo scripts run in
  interactive terminals.
- Keep regular history out of scope for now; show only a disabled History menu
  option.

## Three UX deliverables

This is the scope of the redesign. The existing production UI is implementation
baseline only; its current screens and interaction flow are not acceptance
criteria. Do not spend this effort polishing the old direction or adding
unrelated reliability features. Change Rust behavior only where the agreed UX
requires it, with command-boundary tests for that behavior.

| # | Deliverable | Required outcome | UX specification |
|---|---|---|---|
| 1 | **New-work flow and workspace/task workbench** | Replace separate ad hoc creation paths with one intent-first New flow: review the structured proposal, preserve the original request, edit the unsent starting prompt, then create a workspace or task and open its correctly scoped terminal. The workbench keeps workspace and task selection visible, supports a useful workspace with no repos/tasks, and gives the selected owner a full-size interactive terminal. Failed initialization leaves no empty owner. | [New work](docs/ux/screen-new-work.md), [workbench](docs/ux/screen-workbench.md), [no selection](docs/ux/screen-no-selection.md) |
| 2 | **Quick Requests** | Route Quick Request creation through New; keep recent requests prominent in navigation; provide the separate full-list sliding view with back navigation; open the selected request in its correct terminal. | [Quick Requests](docs/ux/screen-quick-requests.md), [New work](docs/ux/screen-new-work.md) |
| 3 | **All remaining documented UX** | Deliver every screen and interaction currently documented in `docs/ux` that is not already covered by deliverables 1 and 2. This includes change review and README browsing, plus repository tools and OS handoff as specified in the workbench UX. Change review is a conventional two-way diff against current `origin/main`; README entries show full paths. No currently documented UX screen or interaction is out of scope. Implement in dependency/readiness order, one end-to-end sub-slice at a time. | [UX index](docs/ux/index.md) and all remaining linked specifications, including [change review](docs/ux/screen-change-review.md), [READMEs](docs/ux/screen-readmes.md), and [workbench](docs/ux/screen-workbench.md) |

Deliver in order, one user-visible end-to-end slice at a time. Each slice
includes necessary Rust behavior, Tauri boundary, frontend experience, and
automated tests; do not split those into separate frontend/backend/testing
projects. Do not start deliverable 2 before deliverable 1 passes its delivery
gate, or deliverable 3 before deliverable 2 passes its gate. Inside deliverable
3, choose one sub-slice at a time; do not invent priority among them.

### Immediate next step

Start deliverable 1 by comparing the current production screen and command flows
to the three linked specs, then implement the specified New-work and workbench
experience end to end. Treat current controls and layout as replaceable, not as
the intended direction. The task-initialization rollback fix is supporting
behavior only; it does not complete this UX deliverable or authorize moving on
to Quick Requests.

## Manual validation gates — three total

Perform one consolidated manual Wayland validation after each of the three
deliverables:

1. **Workspace/task workbench:** after item 1 is complete, validate workspace
   and task creation, selection, and interactive OpenCode work.
2. **Quick Requests:** after item 2 is complete, validate recent navigation,
   the full-list slide/back flow, and interactive request work.
3. **All remaining documented UX:** after every remaining screen and
   interaction in `docs/ux` is implemented, validate the complete deliverable 3
   scope, including change review, README browsing, repo-tool terminals, and OS
   handoff.

These are the three planned manual validations. Run automated tests for each
end-to-end slice as it is completed. If a manual gate finds a defect, fix it
before proceeding; retest that gate rather than starting the next delivery item.
