# OpenCode terminal integration

**Research date:** 2026-10-11  
**Decision for the integration prototype:** Host OpenCode's own interactive TUI in a PTY managed by the Tauri/Rust process. Use the OpenCode server API to create the session, admit the initial prompt, and retrieve history/status; connect the TUI to that same server and explicitly select its session ID.

This preserves the approved direction in [`.opencode-handoff.md`](../../.opencode-handoff.md) and the terminal requirement in [`.requirements.md`](../../.requirements.md). It is a prototype recommendation; it does not change either document.

The shared implementation sequence, runtime contracts, failure modes, and acceptance checks are captured in [`../../docs/opencode-terminal-e2e.md`](../../docs/opencode-terminal-e2e.md).

## Verified facts

### OpenCode has two different server/CLI contracts

- The published [Server](https://opencode.ai/docs/server/) and [CLI](https://opencode.ai/docs/cli/) pages document the earlier API: `opencode serve`, a TUI that is a client of the server, and `opencode attach <url>`. `attach` accepts `--dir` and `--session`. The documented API has session create/list/status, prompts, history, SSE events, and permission replies. The [documented endpoint list](https://opencode.ai/docs/server/#apis) does not describe a user-question/form reply route.
- The current [OpenCode v2 introduction](https://opencode.ai/v2/docs/) identifies v2.0.6 and says normal CLI clients use a shared background server by default. Current upstream source at commit [`38454c6`](https://github.com/anomalyco/opencode/commit/38454c6e9c51f9eb1f98fcec0060ef434f378bb8) defines a different CLI surface: the full TUI takes root `--server` and `--session` options, and `--standalone` selects a private server; the v1 `attach` subcommand is not in that command definition ([CLI source](https://github.com/anomalyco/opencode/blob/38454c6e9c51f9eb1f98fcec0060ef434f378bb8/packages/cli/src/commands/commands.ts)). The current session API is under `/api/session` and can create a session at an explicit directory ([API schema](https://github.com/anomalyco/opencode/blob/38454c6e9c51f9eb1f98fcec0060ef434f378bb8/packages/protocol/src/groups/session.ts), [handler](https://github.com/anomalyco/opencode/blob/38454c6e9c51f9eb1f98fcec0060ef434f378bb8/packages/server/src/handlers/session.ts)).
- **Handoff conflict:** using v2's default shared background server would add an independently managed server, against the handoff's instruction not to add a separate background service. The prototype must use and verify the installed release's private/app-owned server mode. If that cannot be made to work, surface it as a decision rather than silently adopting the shared service. The startup compatibility check must identify the version and matching API/CLI contract; do not mix v1 routes or `attach` syntax with v2.

### Session, approval, and event behavior

- In both contracts, OpenCode owns conversations and the app associates each workspace/task/request record with an OpenCode session ID. For active work, always attach by that stored or newly returned ID; never infer a regular session from whichever session is newest in a directory. Quick Requests share one directory and the prototype's **Reopen latest** recovery affordance selects the newest populated Quick Request session only when no request record is available. Sessions have separate histories; their files are still in the shared directory.
- V2 source includes session-scoped permission list/get/reply routes, with `once`, `always`, and `reject` decisions ([permission API](https://github.com/anomalyco/opencode/blob/38454c6e9c51f9eb1f98fcec0060ef434f378bb8/packages/protocol/src/groups/permission.ts)). It also includes pending session forms with list/get/reply/cancel operations ([session API](https://github.com/anomalyco/opencode/blob/38454c6e9c51f9eb1f98fcec0060ef434f378bb8/packages/protocol/src/groups/session.ts), [form handler](https://github.com/anomalyco/opencode/blob/38454c6e9c51f9eb1f98fcec0060ef434f378bb8/packages/server/src/handlers/session.ts)). These routes are described as experimental in the generated API. The v1 published API table documents permission replies but not form replies. The TUI path therefore has the clearest route to the full existing OpenCode interaction without depending on a custom GUI's coverage of every prompt type.
- The v1 docs expose `/session/status` and an SSE event stream. V2's status event has `busy`, `idle`, and `retry` values ([status schema](https://github.com/anomalyco/opencode/blob/38454c6e9c51f9eb1f98fcec0060ef434f378bb8/packages/schema/src/session-status-event.ts)). V2's `session.active` endpoint only reports foreground execution owned by that process; an absent session is **inactive**, not proof it is complete ([session API schema](https://github.com/anomalyco/opencode/blob/38454c6e9c51f9eb1f98fcec0060ef434f378bb8/packages/protocol/src/groups/session.ts)). Pending permission/form records are needed to identify “waiting for input”; `session.execution.succeeded/failed/interrupted` events can help distinguish completion ([durable session events](https://github.com/anomalyco/opencode/blob/38454c6e9c51f9eb1f98fcec0060ef434f378bb8/packages/schema/src/session-event.ts)).
- V2 labels its general event stream volatile: a slow consumer can lose the stream, and disconnects miss events. It has an experimental per-session durable log with an `after` cursor and a replay-to-live sync marker ([event API](https://github.com/anomalyco/opencode/blob/38454c6e9c51f9eb1f98fcec0060ef434f378bb8/packages/protocol/src/groups/event.ts), [session log API](https://github.com/anomalyco/opencode/blob/38454c6e9c51f9eb1f98fcec0060ef434f378bb8/packages/protocol/src/groups/session.ts)). Filter events by session ID and reconcile current session state and pending requests on reconnect; do not assume an uninterrupted event stream. Whether these signals reliably produce the product's three status labels remains a prototype check.

### PTY, Tauri lifecycle, and platform fit

- OpenCode does not document an embeddable TUI widget. It documents a terminal CLI client; hosting that client means providing a real PTY and terminal renderer. [Tauri's shell plugin](https://v2.tauri.app/plugin/shell/) can spawn processes, while [`portable-pty`](https://docs.rs/portable-pty/0.9.0/portable_pty/) exposes PTY allocation, process spawn, input/output, and resize. [`xterm.js`](https://xtermjs.org/docs/) is a browser terminal renderer. Tauri recommends [Channels for ordered, high-throughput streams](https://v2.tauri.app/develop/calling-frontend/#channels), which suits PTY output better than its general JSON event system.
- The OpenCode TUI sends an XTGETTCAP DCS query (`Ms`) during terminal startup. A raw PTY harness stayed blank until it received the unsupported-capability reply (`DCS 0+r4d73 ST`), after which the TUI rendered its existing conversation. In xterm.js, `+` is an intermediate in this DCS matcher (`{ intermediates: '+', final: 'q' }`), not a prefix; prefix only accepts `<`, `=`, `>`, or `?`. Registering `+` as a prefix raises `prefix must be in range 0x3c ..0x3f`. The regression test uses the actual xterm.js parser. Separately, the Tauri window needs `core:event:allow-listen` to receive Rust-emitted PTY output; without that capability, the session tab opens while xterm stays empty. The built GUI was then verified to render the saved `2+3` prompt and `5` response.
- Tauri reports window close requests separately from app exit ([`WindowEvent`](https://docs.rs/tauri/2.12.3/tauri/enum.WindowEvent.html)) and supports app-managed state ([state management](https://v2.tauri.app/develop/state-management/)); a close request can be prevented and the window hidden while Rust state keeps the server and PTYs alive. This matches the handoff's lifecycle: closing a view/window keeps work running while the Tauri process remains alive; full app quit stops it. Do not tie PTY destruction to a tab's DOM unmount.
- The current v2 source also has experimental session-scoped persistent-PTY endpoints with WebSocket attach, resize, output replay, and controller/observer roles ([handler](https://github.com/anomalyco/opencode/blob/38454c6e9c51f9eb1f98fcec0060ef434f378bb8/packages/server/src/handlers/persistent-pty.ts)). Its implementation launches a detached, unreferenced `opencode-pty` daemon ([daemon source](https://github.com/anomalyco/opencode/blob/38454c6e9c51f9eb1f98fcec0060ef434f378bb8/packages/core/src/persistent-pty/daemon.ts)). This could make view detach/re-attach easier, but its experimental status and extra daemon lifecycle make it a poor default under the approved no-extra-service direction.
- Tauri uses WebKitGTK on Linux and WKWebView on macOS ([process model](https://v2.tauri.app/concept/process-model/)); `portable-pty` documents Unix and cross-platform PTY interfaces. OpenCode v2 publishes both Linux and macOS CLI builds ([v2 downloads](https://opencode.ai/v2/docs/)). Linux-first Tauri/Rust PTY hosting is therefore a plausible macOS-portable direction, but terminal keyboard input, clipboard, resize, and rendering still need a macOS WebView check.

## Viable paths

| Path | Fit and tradeoffs |
|---|---|
| **OpenCode TUI in a Tauri-managed PTY — recommended** | Preserves the fully interactive terminal requirement and OpenCode's own handling of prompts and approvals. API-created session IDs keep the TUI, API history, and SQLite association aligned. Costs: PTY/process management, a terminal renderer, and exact-version CLI compatibility. |
| **Build the conversation UI on the server API** | Direct access to structured messages, status, permissions, forms (in v2), and history; straightforward to style and connect to app navigation. Costs: reimplement the interactive OpenCode experience and keep up with all user-input/tool interaction types; v1 docs do not establish a form-answer API, and v2 APIs cited here are marked experimental. **Conflict:** replacing the embedded terminal would change the approved product requirement and handoff direction. |
| **OpenCode v2 persistent-PTY API** | Server-managed PTYs can be reattached over WebSocket with replay and resize. Potentially useful if a Tauri-owned PTY proves fragile. Costs: experimental API plus detached helper daemon and more complex shutdown/handoff ownership; not the first prototype path. |

## Assumptions to test

- The installed OpenCode 1.18.35 release supports an app-owned `serve` process, API session creation, and `attach` to an API-created session. A Linux smoke check confirmed the TUI stayed connected to a newly created session in a PTY; it did not send a model prompt.
- The runnable prototype's saved-session restore was exercised through the built Tauri GUI: **Reopen latest** selected a populated session instead of a newer empty record, attached its TUI, and visibly rendered its prompt and answer without sending another model prompt. A fresh model-backed streaming response and same-session follow-up remain to be checked; hiding and reopening the terminal/window are also available.
- `busy`/`idle`/`retry`, pending permission/form requests, and execution outcome events can be combined into the product's running/waiting/completed states without races. In particular, “inactive” alone is not treated as completed.
- `portable-pty` plus the chosen terminal renderer behaves acceptably in Linux WebKitGTK and macOS WKWebView for keyboard input, clipboard, resize, and reconnect.

## Recommendation and prototype question

Proceed with one app-owned, private OpenCode server for the Quick Requests directory. Create each request through that version's server API with an explicit directory, store the returned session ID, then start the version-matched full TUI in a Rust-owned PTY connected to the same server and session. Once the TUI is attached, admit the initial prompt through the API so the terminal is listening before generation starts; use the terminal for interactive follow-ups and user input. For the documented v1 CLI, attachment is `opencode attach <url> --dir <directory> --session <id>`; current v2 source instead defines root `--server` and `--session` options. Confirm the exact invocation against the installed binary before relying on it. Keep the PTY/TUI client alive when its view is hidden; keep the Tauri process alive when its window is hidden; stop the app-owned server and PTY children on full quit. Use API events/state for status and SQLite associations, not a second transcript.

**Primary manual prototype question:** When a user submits a Quick Request, does the GUI automatically open the corresponding interactive OpenCode session soon enough for the user to inspect the response as it streams, then enter a follow-up in that same session?

**Supporting integration question:** Can the installed OpenCode version support two TUI clients, each explicitly attached to a separately API-created session in the same directory, with approvals/user-input working, while closing and reopening a view/window leaves the server-side session running and correctly reconnectable?

### Minimum experiment and acceptance checks

The small Tauri/Rust/raw-HTML shell is implemented in [`../quick-request/`](../quick-request/). The primary acceptance check is user-operated: follow [`quick-request-manual-verification.md`](quick-request-manual-verification.md) and demonstrate that a Quick Request opens its interactive OpenCode session before generation, streams output in that view, and accepts a follow-up in the same session. API success alone does not pass this check.

Use these supporting checks to verify the integration behind the manual flow:

1. Startup reports the OpenCode version and verifies the matching server endpoint, private-server mode, and TUI attach/session flags.
2. Create two sessions at one directory via the API; launch one TUI per ID, then submit distinct initial prompts through the API. Each TUI shows the matching response/history and API events while both sessions share the expected filesystem directory.
3. Exercise a follow-up prompt, one tool approval, and one OpenCode user-input/question request in each TUI; the correct session resumes after input.
4. Observe running, pending-input, and completed outcomes. After an event-stream disconnect, reconcile from API state and pending permission/form lists; do not label an inactive session completed without evidence.
5. Hide a terminal view and close/hide the Tauri window during active work. Reopen both and confirm the same session IDs, live state, and usable terminal interaction. Confirm full quit ends the app-owned execution as specified.

If checks 2–3 fail because session attachment or input is not supported by the installed CLI, test the v2 persistent-PTY path as a separate, explicitly experimental follow-up. Do not switch to an API-rendered conversation UI without reopening the approved requirement.

The current prototype does not yet implement GUI status classification from OpenCode events or verify API event recovery, and macOS terminal rendering/input remains untested. Those checks follow the primary manual Quick Request flow.
